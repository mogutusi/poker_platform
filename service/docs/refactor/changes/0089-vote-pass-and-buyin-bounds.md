# 0089 · 免盲投票走完整流程 + 房间买入额越界(0082·B)

日期:2026-08-24 · 性质:**验证先行**· 触发:[TODO.md](../TODO.md) 「前端页面与功能」0082·B。

## 为什么这一项

[0082](0082-vote-config-and-hand-end-status.md) 把投票面板与房间配置接上了界面,[0084](0084-new-here-channel.md) 让 `new_here` 有了传达渠道,[0088](0088-betting-floor-and-vote-on-the-wire.md) 又补上了「投票人集合变了要说出来」。但**从来没有人在浏览器里把一张票投到通过**——现有用例只走到「有人能表态」为止,通过之后会发生什么(新人真的免掉入局盲、下一手被发牌)一次都没验过。

同样地,房间买入额的越界拒绝(`INVALID_BUY_IN`,由 shell 按 `gameconfig` 上下限挡)只有后端测试盖着。

本仓的经验很一致:这一层每次都能抓到前两层看不见的东西(0079/0080/0082/0085/0087)。

## 开工前已经看出的一处可疑

`free_entry_vote_closed` 在前端只做一件事:`set({ freeEntryVote: null })` —— **面板直接消失,不告诉任何人结果**。投票通过还是被否决、谁被免了,用户完全看不到。`FreeEntryVoteClosed` 明明带着 `passed` 与 `waived`。

这不是「前端复算规则」,是**服务器已经说了、界面丢掉不用**。留到验证阶段确认它在真界面上确实什么都不显示,再修。

## 打算怎么做

1. **扩 `e2e/vote-config.spec.ts`**:把现有那场投票投到**全票通过**,断言:
   - 界面给出结果(通过 / 被免的是谁),而不是面板凭空消失;
   - 通过之后新人**下一手真的被发牌**,且**没有多付一个大盲**(与「不投票直接开局」对照)。
2. **补房间买入额用例**:在配置面板里填一个越界值,断言被服务器拒(`INVALID_BUY_IN` 的中文文案),且当前买入额没变;再填一个合法值,断言 `room_config_changed` 回来后面板与开局默认值都跟着变。
3. **修验证抓到的东西**,动行为前先读该行为的设计文档。

## 实际改了什么

按计划落地。开工前那处「可疑」被证实,另外**验证过程本身抓到一条测试基础设施缺陷**。

### 一、投票结果要说出来(开工前就看出的那处)

`free_entry_vote_closed` 此前只做 `set({ freeEntryVote: null })` —— `passed` 与 `waived` 直接丢掉。界面上的表现就是**面板凭空消失**:投没投过、通没通过、谁被免了,一个字都没有。

修法:store 留一份 `lastVoteResult`(服务器给的 `passed`/`waived`),`FreeEntryVote` 组件在没有进行中投票、但有结果时改渲染一张结果卡(通过=绿、没通过=红,并点名被免的是谁),可手动关,新一手 `hand_started` 自动清(与 `HandResult` 同款生命周期)。**这不是前端复算规则**——两个字段都是服务器说的,此前只是丢掉不用。

### 二、投到通过的完整流程(浏览器)

`e2e/vote-config.spec.ts` 的投票用例接着往下走:B 补上最后一票 → 全票通过 →

- **三方(投票人 A/B、候选 C)都看到结果卡**,且点名 `carol`;
- 紧接着开一手,**C 真的被发牌**(他自己那两张正面牌出现),
- **底池只有 SB+BB = 3**。C 若没被免,入局要**额外**付一个大盲,底池就是 5。
  - 如实记这条断言的边界:三人桌两个盲位,C 恰好坐在盲位上时两种情况都是 3,所以它是**必要条件**而非充分条件(免盲生效时恒为真,不生效时多数情况会红)。「一分不多收」的穷举在 core 层的 waive 用例里。

### 三、买入额越界(浏览器)

新用例:配置面板填 `100000001`(超 `MAX_BUY_IN`)→ 服务器回 `INVALID_BUY_IN`,界面显示中文文案,**当前买入额一分没动**;再填 `250` → 广播回来面板跟着变,**而且入座时真的按 250 买进去**(`data-seat-points` 断言)。前端不预判上下限,照发让服务器裁决——上下限归 shell(core 不 import 配置)。

### 四、验证过程抓到的:结束时还停在手牌里的用例,会卡住下一个用同名账号的用例

新用例单跑绿、进全套必红,报的是「找不到『房间设置』按钮」——离真因很远。查下来:`table`/`raise`/`reconnect` 打完就关浏览器,人还坐在牌桌上且**手牌没打完**;下一条用例拿同名账号登录走「先退再进」,而**局中的 `leave_room` 要等这手打完才驱逐**([rules.md](../../rules.md) ④),于是它连房都进不去,`RoomConfig` 因 `state.room === null` 整个不渲染。

这是 [0079](0079-browser-e2e-and-cors.md)(账号互相顶替)、[0086](0086-retire-plaintext-endpoint.md)(筹码跨用例流动)之后**同一条教训的第三种形态**。修法同 0086:给需要真进房的用例一个专属 dev 账号(`gina`),并把这条写进 [frontend/docs/dev.md](../../../../frontend/docs/dev.md)。`DEV_USERS` 只可追加(`_dev_uid(index)=index+1`,改序会错配已有行),追加是安全的。

## 自 review

按 [review.md](../../review.md) 七维。本批性质是**补验证 + 一处界面修复**,最高风险面是「验证会不会假绿」与「新加的断言是不是真的在验它自称验的东西」。

- **① 分层 / 不变量**:后端逻辑零改动(只追加一个 dev 种子账号)。前端新增的结果卡**只渲染服务器给的 `passed`/`waived`**,不判定、不推算(前端不变量 1)。`data-seat-points` 是测试钩子,值取自服务器的 `SeatView.points`,不引入第二份事实。
- **② 代码↔文档同步**:[frontend/docs/state.md](../../../../frontend/docs/state.md) 事件表补「`Closed` 要显示结果」;[frontend/docs/dev.md](../../../../frontend/docs/dev.md) 补「停在手牌里的用例会卡住下一个」;`poker.env.example` 的 `DEV_USERS` 注释写清 `gina` 的由来。协议没变,故 BACKEND_GUIDE 不动。
- **③ 文档↔文档一致**:[TODO.md](../TODO.md) 勾掉 0082·B 并写清抓到了什么。本篇链回 0079/0082/0084/0086/0088。
- **④ 数据模型正确性**:`lastVoteResult` 与既有 `lastResult`(手牌结算)同形同生命周期(展示后可手动关、新一手自动清),不引入新的状态机;`null` 表示「没有待展示的结果」,与「有投票进行中」互斥地由 `freeEntryVote` 表达,两者不会同时渲染。
- **⑤ 规范合规**:测试钩子一律 `data-*`/`data-testid`,不按文案定位;新增字段带中文注释;无魔法数(`100000001` 是相对 `MAX_BUY_IN` 的越界值,注释写明出处)。
- **⑥ 测试充分**:3 处反向变异确认。**如实记两处缺口**:(a) 「底池 = SB+BB」是必要条件不是充分条件(见上一节的边界说明);(b) 投票**被否决**那条路径(有人点「反对」)界面上没验,只验了通过——否决的结果卡走的是同一段渲染,但没有用例钉住。
- **⑦ 流程账本**:本篇即账本,开工前写「打算」并点名那处可疑,收工回填。与打算相比多出一件(测试账号耦合),已单独成节。
