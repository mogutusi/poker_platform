# 0107 · 套件买不起入场费时,至少把话说清(BUG-21 ③)

日期:2026-08-28 · 性质:**测试基建(前端 e2e 脚手架)**· 触发:[BUGS.md](../BUGS.md) BUG-21 —— dev 账号积分只出不进,浏览器套件迟早会红,而症状指向界面。0106 收工复跑真撞上了:`dave` 只剩 96、买入 100,`reconnect.spec` 红在「Ready 不可点」上,查了一圈界面才发现是钱的事。

## 修哪一半,先说清

BUG-21 登记了三个修法:① 跑前把 dev 账号拉回种子值;② 用例结束归还筹码;③ 让 `joinTable` 的失败自己解释自己。**本批只做 ③**:

- ③ 消掉的是「症状骗人」——那一半是 0106 实际付掉的时间成本。
- ① 需要一个能安全触达 DB 的前置钩子,而 DB 不是权威(内存才是):套件起跑时若上一轮有人还挂在 world 里,直改 DB 会跟 delayDB 的回灌打架。要做对得走「dev 专用端点」或「重启后端」,那是测试基建的**设计决定**,不该混在一个改报错信息的批里顺手拍。
- ② 对「结束时还停在手牌里」的用例(table/raise/reconnect)本来就做不到——局中离房要等手牌打完,这正是这些账号被专用化的原因(0089)。

所以 BUG-21 **不划掉**:漏水的机制还在,本批只是把水表装上了。条目里注记 ③ 已做。

## 打算怎么改

`frontend/e2e/helpers.ts` 的 `joinTable`:买入后等 Ready 可点的那一步,失败时不再裸抛 expect 超时——先看界面上有没有服务器的拒绝(`action-error`),有就抛一条**指向积分**的错误:带上服务器的 `detail`、这个账号名、以及「多半是 BUG-21,恢复法见 BUGS.md」的指引。没有拒绝再原样抛(那才是真的界面回归)。

**验证方式就按 BUG-21 登记的判据**:把一个 dev 账号的积分临时调到买入额以下,跑一条只调 `joinTable` 的探针,确认报错文本指向积分而不是界面;恢复原值后全套复跑。积分在 DB 里改是安全的:该账号此刻不在任何房里 ⇒ 不在 `world.users` ⇒ 下次 `join_room` 会重新从 DB 载入(0073 的载入屏障),不需要重启后端。

## 实际改了什么

按计划,两处:

- **`frontend/e2e/helpers.ts`** `joinTable`:等 Ready 可点那步包 `try/catch`——超时且界面上挂着服务器拒绝(`action-error`)时,抛出的错误带三样东西:服务器的 `detail`(如 `have=50 need=100`)、BUG-21 指引、恢复法(「该账号不在房时改 DB 即可,下次进房会重新载入」——这半句被探针顺带验证为真,见下)。没有服务器拒绝就原样重抛,不吞真正的界面回归。
- **[BUGS.md](../BUGS.md)** BUG-21:注记 ③ 已做、①/② 未做、**条目不划掉**(漏水机制还在,本批只装了水表)。

## 验证

**判据照 BUG-21 登记的写法真跑了一遍**(一次性探针,用完删):

1. DB 里把 `alice` 调到 **50** 分(买入额 100)。**不重启后端**——她不在任何房里 ⇒ 不在 `world.users` ⇒ 下次 `join_room` 经 0073 的载入屏障从 DB 重新载入。这一步同时验证了错误信息里「改 DB 即可」那半句不是想当然。
2. 探针调 `joinTable(alice)`,拿到的报错第一行是:`joinTable(alice) 买入被服务器拒绝:have=50 need=100`,后随 BUG-21 指引与恢复法——**指向积分,不指向界面**。修复前同一情形的报错是裸的 `expect(ready).toBeEnabled() timeout`(0106 实付的排查成本)。
3. **清理有讲究,记下来**:探针里 alice 入了座(买入被拒后 0 筹码占座),上下文一关就是 OFFLINE 保座,90 秒后 cleanup 会把内存里的 50 分经 `PointsWrite` 落库——**先恢复 DB 再等到 cleanup 落库,恢复就会被 50 盖掉**。所以顺序是:先重启 uvicorn(清掉幽灵与待落库值,按房规验证重启生效:杀 pid → 端口释放 → 新 pid 217142 → errno 98 日志 0 条),再把 alice 恢复到探针前的 **998**(不是种子值 1000——探针只该撤销自己,998 里那 2 分的流失是 BUG-21 机制在正常运转,不该被顺手抹掉)。

- **⑦ 流程账本**:变更记录先行;探针清理的顺序坑(先重启再恢复,否则 cleanup 落库盖掉恢复值)写进验证段——那是下一个跑这种探针的人必踩的。
