# 0075 · 设计文档全面精简(可读性优先,意思不变)

日期:2026-08-17 · 性质:**文档改写 + 少量代码注释同步**(零行为改动)· 触发:用户「services/docs 下的架构 md 们写得非常繁琐,不简单、不易懂,许多奇怪的术语,明明可以简单地说明情况——对它们进行全面的精简」,并要求「不要与原来的意思出现分歧」。

> 范围 = `service/docs/` 下 25 篇设计文档(不含 `changes/`;`changes/` 是历史台账,按约定只追加、不重写)+ 8 处按行号引用文档的代码注释。

## 结论一句话

25 篇文档全部重写,**字符数减少 10%**(不含任务清单 TODO.md:209587 → 188491),真正的改善在结构:自造修辞术语清零、信息墙拆成短句、每节开头给一句话结论。三轮改写 + 三轮对抗核实共确认 **38 处语义漂移并全部修掉**,其中 **3 处是改写引入的真错误**(见「实际改了什么」④)。718 测试全绿。

## 病根诊断(先诊断再动手)

用户说的「繁琐」不是单纯字数多。通读后定位到三个具体毛病:

1. **一句话塞多个事实**。大量 bullet 是「主张 +(出处)+ 条件 +(例外)+ 阈值 +(决策号)」挤成一行,读者必须反复回读才能拆开。messaging.md 有一条 bullet 塞了 9 个独立事实。
2. **括号套括号**。补充说明层层嵌套,主干句被打断。
3. **自造修辞术语**。「绿测」「入账」「猎杀」「换靶」「双签」「红利」这类比喻只有作者自己懂;加粗被滥用到失去强调作用。

## 关键设计决策

1. **意思不许变是硬约束,字数下降只是副产品。** 每轮改写后都跑对抗式核实(对照 `git HEAD` 逐文件比对),找 dropped-fact / altered-semantics / invented-claim / broken-link / identifier-changed / heading-changed 六类漂移。核实者默认先试图反驳自己的候选发现,驳不倒才算数。
2. **项目正式术语保留,不算「奇怪术语」。** 工作副本、commit-or-discard、delayDB、模型 2、staleness、载入屏障、付盲即玩、免盲投票、顶替再连、入站铁序——这些是跨文档与代码共享的词汇,改叫法会造成文档间分裂。做法是保留原词、首次出现补一句白话解释。要消灭的只是**只有作者懂的比喻**。
3. **章节标题与被引用的原词不动。** 代码注释按标题名和原词引用文档,例如 `credentials.py` 引 `docs/auth.md §登录握手`、`channel.py` 引「入站铁序」、`sidepot.py` 引「forfeit」、`gameconfig.py` 引「队列有界」。改标题或换词会静默打断这些引用。
4. **删细节前必须验证它在链接目标里真的存在。**「这段在别处有」是最容易出错的自我说服,要求亲自打开被链接的文档确认,确认不了就保留。
5. **可读性优先于字节数。** 拆长句必然让行数变多,这是接受的代价。

## 打算改什么(开工前)

25 篇按主题分组,每组一名改写者;改完立刻交对抗核实者对照 HEAD 找漂移;确认的漂移交修复者。机械核查兜底:相对链接目标是否存在、反引号标识符是否被吞、数字约束是否被吞、`§` 章节引用与代码注释里的按名引用是否仍能命中。

## 实际改了什么

### ① 三轮改写(每轮解决的问题不同)

| 轮次 | 目标 | 结果 |
|---|---|---|
| 第一轮 | 去自造修辞、砍重复强调、压缩动机铺陈 | 字符 −13%,但重读发现信息墙式长句仍在 |
| 第二轮 | 拆信息墙:一句话一件事、括号降级、多事实拆子条目、术语补白话、每节加「一句话」结论 | 可读性大幅改善,但**拆过头**——字数反弹,rest.md 行数涨了 161% |

第二轮是**必要的中间态**,不是弯路:不先拆开就无法判断哪些是真事实、哪些是复述。但它确实需要第三轮收尾,这一点开工时没预料到。

### ③ 订正了一处原文档的旧错误(实质改动,已对代码核实)

`user.md` 与 `architecture.md` 原本写「登录时从 DB 载入积分」,但 user.md 自己的正文写的是 `JoinRoom`。查代码:[receiver.py:213](../../../app/shell/receiver.py) 是「进房:按连接 nick 读 DB 取 uid/loaded」,[login.py](../../../app/rest/login.py) 只做认证、不读积分。**「登录时载入」是错的**,两篇统一改成「进房(`JoinRoom`)时载入」。这是本次唯一一处有意的语义改动。

### ④ 三处改写引入的**真错误**(已修)

这三条不是措辞漂移,是新造的错误断言,是本次最值得记的教训:

1. **testing.md 编造「付盲即玩 = 当手就能玩」**。rules.md 明写「投一个大盲,**下一手**立刻被发牌」。改写者为「给术语补白话」而自行下定义,把生效时机提前了一手。写进测试清单会直接误导单测断言的手次。
2. **testing.md 编造「免盲投票 = 全桌投票」**。rules.md 明写投票人是「**已入局玩家**」(不含新玩家本人、不含观战/坐出者)。
3. **architecture.md 编造「付盲即玩 = 立刻参与本手」**(第三轮又犯一次,同 1)。

**根因**:合同要求「术语首次出现补一句白话」,但没要求「补之前先去主场文档核对定义」。补白话等于下定义,而下定义就是在新增技术断言。

### ⑤ 代码注释同步(8 处)

`reduce.py`(6)、`test_start_hand.py`、`test_free_entry_vote.py` 里按**行号**引用 rules.md 的注释(如「rules.md ① 行 50」)在重排后全部指错——其中「行 69/73/75」三处改写前就已经指错。行号引用本就脆弱,统一改成「章节 +原文短语」(如 `rules.md ①「入局与防躲盲」`),稳定且可 grep。顺带修掉 `session.py` 引用不存在的 `§token 层级`(实际是 `§密钥层级`,改写前既有的错)。
