# 0080 · 两人同桌走到底:又抓出三个界面缺陷

日期:2026-08-17 · 性质:**前端建设**(后端零改动)· 触发:承接 [0079](0079-browser-e2e-and-cors.md) 待办第 1 条「浏览器用例走完整牌局」。

## 结论一句话

用两个 browser context 模拟两个玩家,在真浏览器里走通「入座 → 买入 → 准备 → 开局 → 弃牌 → 手牌结束」,过程中**又抓出三个缺陷**:观战者根本没有入座入口、开局后页面整个白屏、行动按钮在别人回合仍可点却毫无反应。5 个浏览器用例现已全绿。

## 抓到的三个缺陷

### A · 观战者没有入座入口(界面死路)

牌桌页第一行就是 `if (!seat.player) return null`——**空座位压根不渲染**。原 mock 版给九个座位都塞了假玩家,所以从没暴露;换成真实数据后,进房是观战状态、桌上一个可点的东西都没有,**永远坐不下去**。

修法:空座渲染成一个带 `data-empty-seat` 的按钮,点它发 `sit_down`;已入座的人看到的是禁用态。

### B · 开局后页面白屏

```
TypeError: Cannot read properties of undefined (reading 'length')
```

`const hand = gameStarted ? playerHands[seat.number] : []`——只有**自己的座位**(以及摊牌后被亮牌的人)在 `playerHands` 里有条目,别人一律没有。**这正是隐私边界**:别人的底牌在协议上结构性缺位,不是空数组。原 mock 给所有座位都发了牌,直接读 `.length` 从不出错;换成真实数据后其余座位是 `undefined`,一渲染就整页崩。

修法:兜 `?? []`。一行的事,但没有真浏览器跑一次开局就发现不了——单测不渲染,协议冒烟没有 DOM。

### C · 不是你的回合时,行动按钮仍可点且毫无反应

五个行动按钮从不禁用。`handleAction` 里有 `if (!myTurn) return` 的守卫,所以点了什么也不会发生——**用户看到的是一排点不动却又不像禁用的按钮**,不知道是卡了还是坏了。

修法:按钮加 `disabled={!myTurn}`,并在行动条上方加一行提示——轮到你时说「轮到你行动」,否则说「等待 X 行动」。按钮灰着必须说清在等谁,只灰不说等于没解释。

> 这条也是测试自己暴露的:测试写的是「谁的 Fold 可点就点谁的」,而按钮从不禁用,于是永远点 A 的,轮到 B 时就静默丢弃。**让界面正确表达状态,测试才有东西可依据**。

## 顺带修的:UserStatusChanged 归并不全(状态层)

排查 A 时发现更深一层:后端用**同一条** `UserStatusChanged` 表达三件事,而我的归并只处理了其中一件。

| 情形 | `seat_position` | 我原来的处理 |
|---|---|---|
| 观战 → 入座 | 座位号 | **整条被吞**:只在已有 `seats` 里找人改状态,而观战者根本不在 `seats` 里 |
| 在座内变状态(ready / sit-out / 断线) | 座位号 | 正确 |
| 起身 → 观战 | `null` | **没处理**:人应从 `seats` 移除并回到观战列表 |

所以即便空座可点,点了也不会有任何变化——事件到了却没人管。现已三种情形全处理,并补了三条单测钉住(53 项全绿)。

- **② 代码↔文档同步**:三处修改都在注释里写明了「原 mock 为什么没暴露、真实数据下为什么会错」。`docs/state.md` 描述的事件映射与新的三情形处理一致。
- **③ 文档↔文档一致**:本篇链回 0079。
- **④ 数据模型正确性**:新增座位时 `points` 记 0——**筹码要等 `player_bought_in` 或下一次快照才知道**,不猜、不填假值。
- **⑤ 规范合规**:空座按钮用 `data-empty-seat` 属性给测试定位,不靠文案(改文案不该弄坏测试)。
