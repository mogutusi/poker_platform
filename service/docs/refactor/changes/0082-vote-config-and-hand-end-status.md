# 0082 · 免盲投票 + 房间配置 + 错误文案,并修掉「打不了第二手」

日期:2026-08-20 · 性质:**前端建设 + 一处后端契约补齐**(手尾状态广播)· 触发:承接 [0081](0081-lobby-hub-settings-history-dm.md) 待办第 2 条。

## 结论一句话

接上最后 4 条未接命令(协议覆盖 **15/15**),给错误码补了中文文案;过程中撞出一个**卡住基本玩法的真 bug**——打完一手后开不了第二手,根因是后端手尾改了状态却不广播,前端无从知道。

## 一、免盲投票 + 房间配置(最后 4 条命令)

**免盲投票**(规则见 [rules.md](../../rules.md) ①)。面板要表达清楚三件事:在投什么、还差谁、我能不能投。其中「还差谁」比「已有几票」更值得显示——**全票才通过,任一反对立即失败**,知道在等谁才知道要不要去催。不是投票人的人(比如被投的新人本人)也要看得到进展,所以面板对他们照常显示,只是没有按钮。

**房间配置**(见 [core.md](../../core.md))。三条规则直接落进界面:任何在房成员都能改(没有房主,所以不做权限判断也不藏);**只能两手之间改**,局中提前禁用并说明是「手牌进行中」而不是「你没权限」;大盲不单独设,只给小盲输入框并把 `2×` 算出来的大盲先显示给人看。

## 二、错误码文案

后端只回机器码,文案归前端([error.md](../../error.md))。此前界面把 `NOT_ENOUGH_PLAYERS` 这种码**原样显示给用户**。现在 `src/utils/errorText.ts` 做映射,并加了一条测试:**从 `wire.gen.ts` 里抽出全部 `ErrorCode` 逐个比对**,漏一个就红。这样后端将来新增错误码时会立刻发现,而不是等用户在界面上撞见。

## 三、修掉「打不了第二手」(后端)

这是本轮最要紧的发现,浏览器测试撞出来的。

**症状**:打完一手,界面仍显示「✓ Ready」和「Start Game」,点了却回 `NOT_READY`。而且因为界面以为你已准备好,**根本没有 Ready 按钮可点**——用户彻底卡住,第二手开不了。

**根因**:`_finalize_hand` 把 `PLAYING → SITTING_IN`(局中请求坐出者转 `SITTING_OUT`),但只产出 `HandEnded` / `Persist` / `ClearAction`,**没有任何事件携带这个状态转移**。客户端只能从事件知道状态变化,于是本地那份 ready 状态永远停在上一手。

**先按纪律查过这是不是有意的**:[core.md](../../core.md) §4 结算写了状态转移、[connection.md](../../connection.md) 写了「有座不在手 → `SITTING_IN`(需重新 ready)」,**但事件清单里没有对应事件**。两处文档都把它当成客户端应该知道的事实,却没有传达渠道——是缺口,不是省略(对照 0074·B 的教训:那次是「文档明写了才是有意」,这次是「文档明写了却没实现传达」)。

**修法**:`_finalize_hand` 里每个发生转移的人产出一条 `Broadcast(UserStatusChanged)`,排在 `HandEnded` 之后——客户端先知道「这手怎么结的」,再知道「大家回到了什么状态」。

**为什么修后端而不是前端兜**:前端本可以在收到 `hand_ended` 时自己把 playing 改成 sitting_in,但那是**复算服务器规则**,违反「服务器是唯一真相」;而且会算错——局中请求坐出的人应转 `SITTING_OUT`,前端不知道谁请求过。

已同步 core.md 的事件清单;补了后端测试钉住广播内容、座位号、与 world 一致、以及排在 `HandEnded` 之后。722 测试全绿(原 721 + 这条)。

## 四、一个前端不该做的预判

原本想按「有 `new_here` 候选 + 有已入局投票人」来决定开票按钮显不显示。做不到:**`new_here` 只出现在 `StateSnapshot` 的 `SeatView` 里**,而服务端在 `_start_hand` 末尾重标 `new_here` 时不发任何携带它的事件,所以打完一手本地这份就过期了。

改成:两手之间一直给入口,发出去让服务器裁决,被拒时把 `CANNOT_OPEN_VOTE` 翻成人话(「要么没有等入局的新人,要么没有合格的投票人」)。**「服务器是唯一真相」在这里的推论是:不预判自己不可能算准的东西。**

> `new_here` 这条与第三节是同一类问题(状态变了但无事件携带),只是后果轻得多——只影响一个按钮的显隐,不卡住玩法,所以本轮没动后端。已登在待办。

## 自 review

- **① 分层 / 不变量**:后端改动只在 `_finalize_hand` 追加广播,不改任何状态逻辑;722 测试全绿。前端没有为了让界面好看去复算规则——这正是第四节那个决定的实质。
- **② 代码↔文档同步**:core.md 的结算事件清单已补上 `UserStatusChanged`,并注明为什么必须广播。免盲投票与房间配置的界面文案都对着 rules.md / core.md 核过。
- **③ 文档↔文档一致**:本篇链回 0081 与后端 rules.md / core.md / connection.md / error.md。
- **④ 数据模型正确性**:广播用的是服务端刚算出的权威状态,不是前端推的。
- **⑤ 规范合规**:错误文案表由测试保证覆盖协议全集,不会随后端新增码而静默漏掉。
- **⑥ 测试充分**:81 单测(+3 文案覆盖)、12 浏览器用例(+2 投票与配置)、722 后端测试。**缺口如实记**:(a) 投票只验到「能开票、能表态」,**全票通过后新人真的免盲入局没验**(要三人打两手);(b) 房间配置只验了改小盲,买入额与越界拒绝没验;(c) 私聊两人真实收发仍未验。
- **⑦ 流程账本**:本篇即账本。这轮再次印证浏览器测试的价值——单测和协议冒烟都不会发现「打不了第二手」,因为它们不看界面状态。
