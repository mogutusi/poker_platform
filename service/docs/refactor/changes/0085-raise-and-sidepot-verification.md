# 0085 · 加注 / min-raise / 多人边池:冒烟与界面验证(0078·D + 0080·B)

日期:2026-08-21 · 性质:**验证先行**(先补验证,再修它抓到的东西)· 触发:[TODO.md](../TODO.md)「功能与验证」第二项。

## 为什么这一项值得单独做

到今天为止,**加注这条路一次都没被真正走过**:

| 层 | 覆盖到的动作 |
|---|---|
| 协议冒烟 `npm run smoke` | 只按需跟注推进到摊牌(0078 §5.2) |
| 浏览器 `npm run test:e2e` | 只走 Check/Call(0080 §六自己记的缺口) |
| 后端 core 单测 | min-raise / 边池穷举齐全(0007/0011),但那是纯函数层 |

也就是说:后端规则测得很透,但**从界面点一次加注到服务器接受**这条链,从来没有端到端跑过;三人以上、边池的界面表现同理。0079/0080/0082 的经验是这一层每次都能抓到前两层看不见的东西。

## 开工前已经看出的一处可疑

[rules.md](../../rules.md) ② 的 min-raise 下限是 `last_bet + max(last_raise_size, BB)`,而 **`last_raise_size` 只在 `core/domain.py` 的 `Hand` 里,没有上 wire**。前端因此拿不到真正的下限,现在的做法是:

- 加注金额输入框的 `min` 写成 `callAmount * 2` —— 这个式子在规则里根本不存在;
- 输入为空时回退到 `state.lastBet + state.bigBlind` —— 只在 `last_raise_size ≤ BB` 时才等于正确下限,**别人大额加注之后就会低于下限**,发出去被服务器拒。

这与 [0084](0084-new-here-channel.md) 修的 `new_here` 是同一类病:**客户端需要的一个规则输入没有传达渠道**,于是前端只好自己猜一个。但先不急着定方案——**先把验证写出来,让它自己说话**,这是本仓一贯更可靠的顺序(0079/0080/0082 都是这么抓到真问题的)。

## 打算怎么做

1. **先扩协议冒烟**(最快的信号):在现有两人局之外加一段真加注 —— 一方 raise、另一方 re-raise(触发 `last_raise_size > BB`)、再 call;断言服务器接受,且下注额与底池对得上。
2. **再扩到三人 + 边池**:三个不同买入额的客户端,让短码 all-in 造出边池,断言 `hand_ended` 的分配与守恒。
3. **再上浏览器**:界面上点一次加注 → 服务器接受;三人同桌时的界面表现。
4. **修验证抓到的东西**,每一处都先读该行为的设计文档再动(本仓纪律)。

范围内不含 0078·D 里「断线重连后 seq 继续累加」那半 —— 它属于 **0079·B**,与本篇的下注面无关,单独一批。

## 实际改了什么

验证先行的做法又一次奏效:**写验证的过程本身抓到了三件事**,其中两件当场修了,一件证据确凿但要改协议、单独登记。

### 一、新增两条冒烟

- **`scripts/smoke-client.mjs`(抽出共用脚手架)**:登录握手 + 加密 ws + 收发帧 + 「上一次会话残留」的进房处理。抽出来不是为了好看——这套 60 行直接压在协议面上,再写第三个脚本就是三份副本,而 [0084](0084-new-here-channel.md) 刚给 `user_status_changed` 加过字段:副本漏改一份,就是一个静默失效的冒烟。三个脚本现在共用它。
- **`scripts/smoke-raise-sidepot.mjs`(`npm run smoke:raise`)**:
  - ① 两人局真加注:加到 10 → 制造 `last_raise_size=8` → 断言 `last_bet + BB`(12)**被拒**、`last_bet + last_raise_size`(18)**被接受**,然后把这一手打完。
  - ② 三人局边池:carol 短码 20 推完 all-in,**并且让还有筹码的人在她 all-in 之后再加一次**——第一版没有这一步,大家只是跟平她的 all-in,底池根本没分层,「边池」名不副实(自己写的测试自己先假绿了一轮)。判据改成「分配总额 > 主池上限 3×SHORT」,分层才算数;再断言短码赢取够不着边池。

### 二、当场修的两件

- **底池从来没有渲染过。** `const pot = state.pot` 算出来之后**在 JSX 里一次都没用**——桌上根本看不到底池有多大,边池就更无从判断。写浏览器用例要断言「服务器收下了这一注」时才发现无处可断言。已补上,只渲染服务器给的数、不本地累加。
- **`journey` 用例断言的是「alice 出现在大厅排行榜上」**,而榜只取前 5、积分随每一手牌变动:本批的加注冒烟一跑,alice 掉到第 6,这条就红了。这是测试与共享数据耦合(0079 记过「账号必须隔离」,这次是**数据**没隔离)。改成断言稳定的东西:头像卡显示的是本次登录的这个人(顺带验证 `/user/me` 走通)+ 榜上有真实条目。

### 三、证据确凿但本批不修:BUG-19(min-raise 前端自编下限)

`last_raise_size` 从来没上过 wire,前端够不着,于是自己编了两个式子(`min={callAmount * 2}`、回退 `lastBet + bigBlind`),**在别人大额加注之后都会低于真实下限**。冒烟给出了正面证据:同一局里 12 被 `ILLEGAL_ACTION` 拒、18 被接受。

这是 [0084](0084-new-here-channel.md) 那类病的第二例(客户端需要的规则输入没有传达渠道)。修法同款,但要动 4 条消息 + codegen + 前端,值得单独一篇。已登记 [BUG-19](../BUGS.md),并且 `smoke:raise` 会一直钉住服务端这一侧的语义。

### 四、浏览器:加注第一次被真正点下去

`e2e/raise.spec.ts`:两人同桌(用 dave/eve,与其它用例的账号隔离)→ 开局 → 输入金额点 Raise → 断言**两边**的底池都变大(广播回来的,不是本地画的)+ 没有错误提示 + 加注之后这一手还能往下走。

## 自 review

按 [review.md](../../review.md) 七维。本批的性质是**补验证**,所以最高风险面不是「代码会不会错」,而是**「验证会不会假绿」**——一条永远为真的断言比没有断言更糟,它会让人以为这块测过了。

- **① 分层 / 不变量**:后端零改动。前端只加了一处渲染,且**只渲染服务器给的 `pot`,不本地累加**——累加就会和服务器分叉(前端不变量 1)。
- **② 代码↔文档同步**:BUG-19 连同实测证据一起登记进 [BUGS.md](../BUGS.md);`smoke-client.mjs` 的抽出理由写在文件头(协议一改三份副本要一起改)。前端 `game/page.tsx` 里那句「本地不算底池」的注释与新渲染一致。
- **③ 文档↔文档一致**:本篇链回 0078/0080/0084 与 BUGS.md;[dev.md](../../../../frontend/docs/dev.md) 补了两条新 npm script 的跑法。
- **④ 数据模型正确性**:不适用(未动模型)。
- **⑤ 规范合规**:测试钩子一律 `data-testid`,不按文案定位(改文案不该弄坏测试);冒烟脚本用 dev 种子凭据并注明仅限本地。
- **⑥ 测试充分**:这是本批的正题。**两处「差点假绿」如实记下**:(a) 边池那段第一版只让大家跟平 all-in,底池没分层却照样绿——现在的判据是「分配总额 > 主池上限」,不分层就红;(b) 错误码断言第一版凭印象写成 `INVALID_BET_AMOUNT`/`BET_TOO_SMALL`,真实是 `ILLEGAL_ACTION`,是跑出来才知道的(凭印象写断言 = 把测试写成自己的想象)。**缺口如实记**:三人以上的**界面**表现只验到「三人能开局」(在冒烟层),浏览器用例仍是两人;边池在界面上长什么样(分层显示)没有验,因为界面目前只显示一个总底池。
- **⑦ 流程账本**:本篇即账本,开工前写「打算」(含「先写验证、让它自己说话」的顺序),收工回填。与打算相比多出两件当场修的东西,已如实分节记下。

### 顺带发现,未在本批处理

- **界面只显示一个总底池,不显示分层。** 有边池时玩家看不出「主池多少、边池多少、我够得着哪个」。协议里 `hand_ended` 只给最终分配,进行中并不广播分层信息 —— 要做得先想清楚是否上协议。已记在这里,未登记为缺陷(不是「会错」,是「没做」)。
- **dev 库的积分会被冒烟一路改小**,任何「谁在排行榜前几」的断言都不可靠。本批把 `journey` 改掉了,其它用例暂未发现同类耦合。
