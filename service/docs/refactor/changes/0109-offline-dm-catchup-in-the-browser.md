# 0109 · 私信离线补收进真浏览器(0081·C 的最后一条覆盖缺口)

日期:2026-08-28 · 性质:**浏览器端到端验证(只加测试)**· 触发:[TODO.md](../TODO.md) 0081·C 的余项之一——0103 自 review ⑥(b) 如实记的缺口:「私聊只验了**在线实时投递**,**离线补收**(0040 那条链:收件人不在线时落库、登录时补发)仍然没有浏览器覆盖,那需要一个『发完再登录』的编排」。

## 验的是哪条链

0040 落地的 `deliver_dm_catch_up`:收件人**不在线**时私信落库(未读);收件人(重)连时读 DB、把未读的 `DMDelivered` 补发过来 + 已读回执对齐。协议层这条链有后端测试,**浏览器里从来没走过**——而它恰恰是与实时投递不同的代码路径(实时走在线路由,补收走登录钩子)。前几轮的经验一致:每次把一条路搬进真浏览器都会抓到东西(0079 三个、0080 三个、0087 四个、0089 两个、0103 三个约束)。

## 打算怎么改

`dm-and-account.spec.ts` 加一条:

1. **carol 登录并发私信给 dave,此时 dave 没有任何浏览器上下文**(不是「登录了没开抽屉」,是整个人不在线——这才走离线落库那条臂)。
2. carol 侧断言本地回显(发送本身成立)。
3. **然后才创建 dave 的上下文并登录**。断言:没有人重发任何东西,dave 的抽屉按钮出现未读徽标(补收链把落库的那条推了过来),打开会话能看到**那条准确的文本**(带时间戳,防跟历史库存混淆——这个库跨用例累积)。

### 账号选择(照既有纪律)

用 **carol / dave**,不用既有 DM 用例的 eve / frank:同文件两条用例共用一对账号会让**私信库存耦合**(case 1 读掉的会话、case 2 的未读计数互相污染断言)。carol / dave 在本用例**全程不进房**,所以不踩 0089 的占座坑;两人被 raise/reconnect/vote-config 使用都在**本 spec 之后**(按字母序 dm-and-account 最先跑),届时本用例的上下文早已关闭,顶替语义(0087)保证互不干扰。

## 实际改了什么

按计划,一条新用例进 `frontend/e2e/dm-and-account.spec.ts`(**产品代码零改动**),外加 [TODO.md](../TODO.md) 0081·C 划掉这半条。编排与计划一字不差:carol 发时 dave **没有任何上下文**;dave 随后才登录,断言未读徽标 + **准确文本**(带时间戳——这个库跨用例累积,断言到字面才排除「徽标来自历史库存」)。

计划里没有、写出来才确认的一点:**不复用 eve/frank 是对的**——变异实验(见下)会让这条用例红在「消息落库了但没人补收」上,那条未读会留在库里;要是跟实时用例共用账号,下一次跑实时用例的未读计数就被这条残留污染。carol/dave 的库存只归这条用例自己脏。
